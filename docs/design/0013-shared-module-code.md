# 0013 · Shared module code

**Status:** proposed · **Topic:** what a `warm` or host-mode process does
when its step modules carry the same dependencies, so that its memory grows
by one dependency closure per module loaded: the `shared` record that
[0006](0006-module-state.md) left for a host's measurement.

## Context

[0006](0006-module-state.md) keeps one instance of each script's bundle per
process (`warm`, D1). Each bundle inlines its own copy of everything it
imports, as Windmill's bundles do
([WR-27](../semantics/languages.md#wr-27),
[WR-47](../semantics/languages.md#wr-47)), so scripts never share module
state, as on Windmill, where every job runs in a process of its own
([WR-1](../semantics/languages.md#wr-1)). The cost is memory: a process
holds one copy of a shared dependency for each script module it has loaded.
0006 left a `shared` mode out of the first edition until a host measured
that `warm` does not fit.

A host has measured it.

- **The host's bundle.** A compiled Bun 1.3.10 host in host mode serves one
  bundle of 53 CommonJS codebase step scripts built by esbuild 0.28.0. The
  step bundles total 364 MB, 6.9 MB on average, because each bundles the
  same large dependency closure.
- **Its memory.** With 34 distinct step modules loaded and eight concurrent
  runs, the host peaks at 2,268 to 2,289 MiB, about 59 MiB per loaded
  module, against a budget of 650 MiB.
  - A soak of 1,000 runs stays between 980 and 2,382 MiB, with no growth
    trend.
  - The engine process stays at 73 MiB.
- **A public synthetic reproduction.** Six Bun scripts each import one
  generated module of 40,000 distinct strings (4.2 MB), with one flow of one
  step and one of all six. The host's resident set after a full garbage
  collection is:
  - 44 MiB at connect;
  - 75 MiB after one module;
  - 121 MiB after six, about 9.2 MiB per further module.

## Measurements

**Method.**

- **Machine and tools:** Apple M4, macOS 26.5.1, Bun 1.3.10, esbuild 0.28.0
  through its Go API in the settings of WR-47, Go 1.27.3.
- **The host:** a program that embeds the host SDK and is compiled with
  `bun build --compile`, as the host above is. It runs host mode on bundles
  that `bundle.Build` builds, and reports two figures: its resident set
  after three full collections (`Bun.gc(true)`) and its peak resident set
  (`getrusage`).
- **Two fixtures**, both generated by
  [cmd/windmill-lite](../../cmd/windmill-lite/README.md)'s `memory_test.go`:
  - **S** is the synthetic reproduction above, rebuilt (test
    `TestModuleMemory`). The shared module has 4.36 MB of source.
  - **C** is a closure shaped like the host's (test
    `TestModuleMemoryClosure`, run with `WL_MEMORY_PROBE` set). It has 34
    CommonJS codebase scripts in the CLI's default format. Each imports one
    module outside the sync folder, and that module imports:
    - mongoose 8.9.5 (with mongodb 6.12.0 and bson 6.10.4);
    - `windmill-client` 1.326.0 and js-yaml 5.5.0;
    - `@babel/parser` and `@babel/types` 8.0.10;
    - a generated CommonJS package shaped like a generated API client:
      90 modules, each a class of 60 methods and a table of request
      schemas.

    Each step's bundle is 6.89 MB. The prototype, outside the repository,
    built all 53 scripts, 379 MB of step bundles. Mongoose 9 is not used:
    it brings bson 7, which calls `node:v8`'s `isBuildingSnapshot`, and Bun
    1.3.10 does not implement it.
- **Three layouts of each fixture:**
  - **per-script**: today's build;
  - **shared-instance**: the shared module listed as a host-provided module
    (D12), so the host's one instance serves every step;
  - **shared-code**: a prototype of this record's decision. A host-provided
    factory compiles the shared module's CommonJS build once per process
    and makes one instance of it for each step module that loads.

- **Code and state.** Of a distinct module's 42 MiB, about 14 MiB is state:
  the objects its dependencies make when they load. The rest is code:
  source text and compiled code.
- **Identical sources.** JavaScriptCore shares some compiled code between
  byte-identical sources, but bundles differ by their entry code.
- **The kept metadata.** The runtime keeps each codebase script's whole
  metadata for the life of the process, including esbuild's metafile (309 of
  431 KB for C), which it never reads: about 0.5 MiB per module.

**Semantic probes.** These ran on Bun 1.3.10, outside the repository, on
C's packages:

- **A model registered twice.** Two scripts each register a Mongoose model
  named `Order`, with different schemas.
  - Per-script bundles, and two instances of one compiled closure: both
    register, with paths `total, _id, __v` and `sku, _id, __v`.
  - Shared chunks, and packages loaded once: the second fails with
    ``OverwriteModelError: Cannot overwrite `Order` model once compiled.``
- **Strict mode.** A codebase script assigns to an undeclared variable.
  - The CLI's CommonJS bundle runs it and returns `1`.
  - The same script as an ES module chunk throws
    `ReferenceError: counter is not defined`.
- **Packages behind a host-provided file.** Listing a file inside the sync
  folder that imports npm packages fails the build: `Could not resolve:
  "@babel/types"`. The shared copy of a listed module inside the folder is
  the Bun build's ([0010](0010-packaging.md)), and that build resolves no
  package from the folder's `node_modules`. The same file outside the
  folder builds, with esbuild, as milestone F3h made it.
- **A compiled host at run time.** A compiled host imports at run time only
  files that need no package. It resolves no package from disk at run time
  (`Cannot find package`), so a module that imports packages must be
  compiled into the host.

**Throughput.** This was measured on the prototype's bundles, on a machine
that was swapping.

- **One-step flow, 300 sequential runs:** 61 to 73 ms in every layout,
  including shared code after all 34 modules had loaded.
- **34-step flow, 100 sequential runs** after a warm-up:
  - shared-instance: 515 to 906 ms;
  - shared-code: 619 to 738 ms in most rounds, with some rounds of 1.4 to
    4.9 s;
  - per-script: 1.07 to 3.44 s, at about 1.9 GiB.

  No consistent difference shows. The slow rounds came with the larger
  live heaps, so collections are the likely cause; G1's benchmarks in host
  mode measure it properly (F8b).

## Options considered

| Option | S, per further module | C, 34 modules, 8 concurrent runs | Module state between scripts | CommonJS codebase scripts |
|---|---|---|---|---|
| per-script (today, 0006) | 6.3 MiB | 1,911 MiB | separate | the CLI's format |
| (a) shared chunks (0006 option 4) | one instance (not measured) | 120–129 MiB (model, 34 modules) | shared | become ES modules |
| (b) host-provided packages | 0.1 MiB (a listed file) | 130 MiB (listed module) | shared, with the host too | unchanged |
| (c1) one instance per package | no effect: S's module is a file | 132 MiB (model, 34 modules) | shared for packages | unchanged |
| (c2) shared code, instance per script | 0.17 MiB | 475–492 MiB | separate | unchanged |

### (a) Shared chunks: [0006](0006-module-state.md)'s option 4

The build bundles the scripts of one bundler and one set of settings
together, with code splitting. A module that two scripts import becomes one
chunk, evaluated once per process.

- **Memory:** one instance of the closure: 120 to 129 MiB for C in the model.
  The runtime loads no chunks, so it was not measured in host mode.
- **Deviation:**
  - **Shared state.** Every module that two scripts import is one instance
    per process, so scripts share its state; the `Order` probe fails.
  - **A new format.** esbuild and Bun split ES module output only. A
    CommonJS codebase script, the CLI's default (WR-47), would therefore
    run as an ES module:
    - in strict mode, as the `ReferenceError` probe shows;
    - without `module` and `exports` of its own;
    - with `require` only because Bun provides it there, which Node would
      not.

    That goes beyond D13.
- **Opt-in:** a module-state mode, `shared`, chosen at build.
- **Trace and manifest:** the mode, and the chunks in the manifest; a new
  deviation.
- **CLI parity:** the parity check is unchanged, since it builds each script
  alone. What runs has another format and layout. Adding a script can move
  code between chunks, which changes other scripts' files.
- **Fresh mode:** unaffected, since a fresh process loads one script; it
  would run the per-script bundles.
- **Fence:** a chunk evaluates in the context of the first invocation that
  loads a script needing it. Its load-time timers and connections are module
  state (milestone C3b), which then serves every script sharing the chunk.
- **Host-provided modules:** their imports become shims inside chunks, as
  they are inside bundles.

### (b) Host-provided package modules

The host contract lists packages, such as `mongoose`, as host-provided
modules. Imports of them resolve to shims, and one instance per process
serves every script: the host's own in host mode.

- **Memory:**
  - Today's D12 for files is the same mechanism. Listing S's module costs
    0.11 MiB per further module.
  - Listing C's shared module, outside the folder, costs 130 MiB with eight
    concurrent runs.
  - Only what is listed is shared, so the host must list nearly its whole
    closure, and memory grows again with every package it misses.
- **Deviation:** D12 widened. A listed package is one instance shared by
  the host and every script, so the `Order` probe fails. The host's version
  of the package, and its import-time configuration, reach the steps
  ([0010](0010-packaging.md), host-provided modules, items 5 and 6).
- **Opt-in:** packages in the host contract's `host_modules`. The contract
  would need each package's version and lock: 0010 refuses host-provided
  packages today because the contract has no place for a lock.
- **Trace and manifest:** the listed packages and their versions. The SDK
  would check the host's instances against them.
- **CLI parity:** unchanged; the runtime's bundles carry shims, as with D12
  today.
- **Fresh mode:** the bundled copy loads once per process, at registration
  rather than when the step's module loads (D12's load effects, 0010 item
  7).
- **Fence:** listed packages load at registration, outside every
  invocation, so nothing they start is fenced, as with D12 today.
- **Host-provided modules:** this option is D12 extended, and it needs two
  changes:
  - **A CommonJS shim.** Most packages are CommonJS, which D12 refuses
    (`host_module_commonjs`) because its shims take export names from a
    static scan.
  - **Packages behind a file inside the folder.** Listing such a file fails
    to build today (the probe above).

### (c1) One instance per package

The build leaves packages out of each script's bundle (esbuild's
`packages: external`), and the harness loads each once per process from one
copy. A module cache that evaluates identical dependency modules once,
keyed by their content, has the same effect.

- **Memory:** about 132 MiB for C with 34 modules, in the model. A compiled
  host cannot load the packages as built, since it resolves none from disk
  at run time, so the harness would need its own resolver.
- **Deviation:** every package, or every identical module, has one instance
  per process, so the `Order` probe fails. Which instance a script gets also
  depends on which other scripts loaded first.
- **Opt-in:** a build setting.
- **Trace and manifest:** the packages and their keys.
- **CLI parity:** the parity check is unchanged. What runs no longer inlines
  packages: tree shaking and interop then work across a package boundary
  that the CLI's bundle does not have.
- **Fresh mode:** one instance per process anyway.
- **Fence:** a package evaluates in the context of the first invocation that
  requires it, and later scripts share what it started.
- **Host-provided modules:** unchanged.

### (c2) Shared code, one instance per script

The build keeps the dependency modules of a group of scripts in one file
per process, and each script makes its own instance of them. This is the
decision below, which describes it in full.

- **Memory:**
  - S: 0.17 MiB per further module.
  - C: 475 to 492 MiB with eight concurrent runs, and 519 to 525 MiB peak
    after 1,000 runs, with 10.6 to 11.1 MiB per further module.
  - All 53 of the prototype's modules: 631 MiB.
- **Deviation:** none in module state. It changes only where dependency code
  is (stack text), and when an ES module dependency initialises relative to
  a CommonJS one (D18).
- **The other aspects:** below, under the decision.

### (d) Other routes

1. **Recycling on a module count** (F3a's `modules` trigger) bounds memory
   by restarting the process. It cannot keep a working set of 34 modules
   under the budget without reloading them over and over: the first load of
   C's 34 modules took 3.6 to 3.8 s. It stays the backstop.
2. **JavaScriptCore's sharing of byte-identical sources** saves 8 of 42 MiB
   per module in the model. Bundles differ by their entry code, so a design
   cannot rely on it.
3. **The runtime's kept metadata** costs about 0.5 MiB per module. F8b keeps
   only the fields the runtime reads.
4. **An uncompiled host** costs 42 rather than 55 MiB per module in the
   model. Hosts compile for deployment, so the target below is set on a
   compiled host.
5. **`fresh`** is not available in host mode ([0006](0006-module-state.md)).

## Decision

A bundle can be built with **shared code** (`windmill-lite build
-shared-code`). It changes what `warm` and host-mode processes load. It does
not change what a script sees of its dependencies: each step keeps its own
instance of every module it imports, as on Windmill.

1. **Build groups.**
   - The scripts that one bundler builds with one set of settings form a
     group: all the Bun-built scripts of the bundle are one group, and each
     codebase entry's scripts are another (WR-47).
   - A group's **dependency modules** are the modules that its per-script
     bundles inline, other than each script's own entry file. That covers
     the folder's and the codebase's other files, and the packages' files.
   - Host-provided modules, and what only they import, stay out (D12).
2. **One closure per group.**
   - The build writes one CommonJS file per group, its **closure**. It holds
     every dependency module that any script of the group reaches, each
     behind the bundler's lazy wrapper.
   - It exports a function that makes a fresh instance: a table from each
     module's key to its initialiser.
   - **Keys.** A module of the folder or the codebase is keyed by its path
     from the sync root. A package's file is keyed by the package's name and
     version, the integrity its lock records (when one does), and the file's
     path inside the package.
   - Two scripts share a module's code exactly when its key is the same in
     their group.
   - The closure is built with the group's settings: the entry's `define`,
     `inject`, `loader` and `banner`, and the define table and env rewrite
     of 0010.
3. **One instance per script.**
   - **The script's module.** Each script's module in the shared layout is
     its own code, with every import of a dependency module resolved to its
     instance's table. A plugin that only maps paths does this, as for
     0010's other transforms.
   - **Making the instance.** When a step's module loads, it makes its
     instance of the closure with its own `module`, `require`, `__filename`
     and `__dirname`. Dependency code that reads them, or that requires a
     file at run time, sees the step's own, as in its per-script bundle
     (WR-50).
   - **When a module initialises.** A dependency module initialises in the
     step's instance the first time the step reaches it. A dependency the
     step never reaches never runs in its instance.
   - **ES module scripts** (Bun-built scripts and `format: esm` entries)
     reach their dependencies through CommonJS interop. A named import is
     then read from the module at each use, so live bindings still hold.
   - **Pruning.** An import that the per-script bundle prunes, such as a
     `sideEffects: false` module whose exports are unused, is pruned in the
     shared layout too.
   - **The cost.** The closure's code is read and compiled once per process.
     What a further step module costs is the state its dependencies make
     when they load.
4. **What differs: D18** ([0001](0001-equivalence-contract.md)).
   - **Stack text.** Stack frames of dependency code name the closure file
     and its lines, not the step's module.
   - **Initialisation order.** A per-script bundle hoists an ES module
     dependency and initialises it before the step first requires a
     CommonJS dependency. In the shared layout, every dependency initialises
     when the step first reaches it, in import order, so the two can run
     their load effects in another order.
   - Nothing else differs, and `fresh` removes D18.
5. **The bundle.**
   - **What stays.** The bundle keeps the per-script bundles byte for byte
     as without shared code. The parity check keeps comparing them with the
     CLI's uploads, and `fresh` runs them, so the uploaded bytes stay the
     CLI's and only what `warm` and host mode run differs.
   - **What shared code adds.** It adds the closures and each script's
     shared-layout module.
   - **The manifest** records `shared_code: true`, lists the closures with
     their digests, and lists D18 among the bundle's deviations. Each
     script's metadata names its closure.
   - **A run's trace** records shared code beside the module-state mode, and
     lists D18 among its deviations.
   - **Open** follows the manifest; `ModuleState: fresh` runs the per-script
     bundles.
6. **The settle-time fence (D9)** is unchanged.
   - Making an instance is part of loading the step's module, which runs in
     the loading invocation's context. The timers and connections that
     dependency code starts while loading are module state, which the fence
     leaves alone (milestone C3b).
   - A dependency that a running invocation first reaches later initialises
     in that invocation's context, as a lazily required module does in a
     per-script bundle.
   - Compiling the closure runs none of its code.
7. **Host-provided modules (D12)** are unchanged.
   - Imports of a listed module resolve to its shim in the shared layout
     too, so it stays one instance shared by the host and every step.
   - A host that wants one instance of a package for its steps lists a
     module that holds it, as today.
   - Host-provided packages (option b) are not added: they would share
     state between steps, which shared code avoids.
8. **Not the default.** A bundle built without the flag runs as today. A
   later record can make shared code the default of `warm` once F8b's suites
   have run both ways.

**Memory target.** The target is the host's budget, for the host's shape:

- **The shape:** a compiled Bun 1.3.10 host serves one bundle of 53
  CommonJS codebase scripts of about 6.9 MB each that share one dependency
  closure.
- **The target:** with 34 distinct step modules loaded and eight concurrent
  runs, its peak resident set stays at or below **650 MiB** through a
  1,000-run soak.
- **On the public closure C,** the prototype holds 475 to 492 MiB with eight
  concurrent runs and 519 to 525 MiB at its peak.
- **F8b's gate** runs C and S with the real shared layout in place of the
  prototype, on the CI runners and on macOS:
  - C: at most 650 MiB peak after its 1,000 runs, and at most 16 MiB per
    further module after a full collection;
  - S: at most 1.5 MiB per further module.
- **On its own bundle,** the host re-measures before it relies on the target.

**Why not the others.**

- **(a), (b) and (c1)** save more memory, but each shares module state
  between scripts, which Windmill never does; the `Order` probe breaks
  under all three.
  - **(a)** also turns CommonJS codebase scripts into strict ES modules.
  - **(b)** also ties steps to the host's package versions and needs the
    host to list nearly its whole closure.
  - **(c1)** also needs a resolver of the harness's own in a compiled host.
- **Shared code** meets the target with the smallest deviation: per-script
  module identity, D1 and the scripts' own semantics stay as in `warm`.

## Consequences

- **What memory tracks.** A further step module costs the state its
  dependencies make when they load (C: about 11 MiB), not their code. A
  host whose dependencies make much state at load still grows per module.
  Its next steps are listing the modules that hold that state as
  host-provided modules (D12, as it stands) and the recycle triggers.
- **First invocations are faster:** C's 34 modules loaded in about 0.55 s
  rather than 3.7 s.
- **The build** makes one more product per script and one closure per
  group.
- **Conformance** gains a configuration: F8b runs the step and flow suites
  in `warm` and host mode from bundles built with shared code. That is the
  cost 0006 named for `shared`, accepted here for a host that needs it.
- **Two findings for 0010** come from the probes:
  - a host-provided file inside the folder that imports packages fails to
    build;
  - a compiled host resolves no package at run time.
- **Two tests in the repository.** `TestModuleMemory` runs S in the three
  layouts wherever the host-mode tests run. `TestModuleMemoryClosure` runs
  C behind `WL_MEMORY_PROBE`, since it needs the network once and about
  2 GiB. Both run the shared-code prototype until F8b replaces it with the
  real layout.

## Conformance cases for F8b

**Step cases** go in `conformance/steps/bun/d18.yaml`. Each runs in `warm`
and host mode from a bundle built with shared code, and in `fresh`, which
runs the per-script bundles. Every case has two or more scripts that share a
dependency module:

| Case | What it holds |
|---|---|
| D18/a | Module state per script: two scripts that count in a shared dependency's state each count their own calls (1 and 1, then 2 and 2 in `warm`; 1 and 1 in `fresh`) |
| D18/b | Identity per script: an object and a class a dependency exports are different for two scripts (`instanceof` across them is false) |
| D18/c | A registry per script: two scripts that each register the same name in a dependency's registry, which refuses a second registration, both succeed (the `Order` probe, synthetic) |
| D18/d | Lazy initialisation: a dependency a script never reaches runs no load effect in its instance; one required inside a function initialises at its first call, and its log line belongs to that invocation |
| D18/e | Initialisation order: a script importing an ES module dependency and a CommonJS dependency, each with a load effect; the per-script order in `fresh`, the shared layout's import order in `warm` (deviation D18) |
| D18/f | Pruning: an unused import of a `sideEffects: false` module runs no load effect in either layout |
| D18/g | A codebase CommonJS dependency's `__dirname`, `__filename` and run-time `require` of an asset are the step's, in both layouts (WR-50) |
| D18/h | Stack text: an error thrown in dependency code has the same name and message in both layouts; its stack names the closure file in `warm` (deviation D18) |
| D18/i | Host-provided modules: a listed module that two scripts and a dependency of each import is the registered instance (D12), while the dependency is per script; the build still warns `host_module_shared_dependency` |
| D18/j | The script's own state: WR-1/a and WR-1/b give in shared code what they give in `warm` |
| D18/k | ES module groups: a Bun-built script and a `format: esm` codebase script read a dependency's live binding (`export let`, changed by a call) after the change |
| D18/l | The fence: a timer a dependency starts while loading is not cleared when the loading invocation settles; one it starts during an invocation is (D9) |

**Build cases** go in `conformance/build/d18.json`:

| Case | What it holds |
|---|---|
| D18/m | Closure membership: a group's dependency modules are in its closure, the scripts' entries and the host-provided modules are not, and a module that two scripts reach is in it once |
| D18/n | Two codebase entries with different settings get two closures; one package version that both reach is in each |
| D18/o | The per-script bundles are byte for byte the same with and without shared code |
| D18/p | The manifest: `shared_code: true`, the closures with their digests, D18 in the deviations, and another bundle digest than without shared code |

**Flow and memory gates.**

- The flow suite runs in `warm` and in host mode from bundles built with
  shared code.
- `TestModuleMemory` and `TestModuleMemoryClosure` run with the real shared
