# 0013 · Shared module code

**Status:** proposed · **Topic:** what a `warm` or host-mode process does
when its step modules carry the same dependencies, so that its memory grows
by one dependency closure per module loaded: the `shared` record that
[0006](0006-module-state.md) left for a host's measurement.

## Context

[0006](0006-module-state.md) keeps one instance of each script's bundle per
process (`warm`, D1). Each bundle inlines its own copy of everything it
imports, as Windmill's bundles do
([WR-27](../semantics/languages.md#wr-27),
[WR-47](../semantics/languages.md#wr-47)), so scripts never share module
state, as on Windmill, where every job runs in a process of its own
([WR-1](../semantics/languages.md#wr-1)). The cost is memory: a process
holds one copy of a shared dependency for each script module it has loaded.
0006 left a `shared` mode out of the first edition until a host measured
that `warm` does not fit.

A host has measured it.

- **The host's bundle.** A compiled Bun 1.3.10 host in host mode serves one
  bundle of 53 CommonJS codebase step scripts built by esbuild 0.28.0. The
  step bundles total 364 MB, 6.9 MB on average, because each bundles the
  same large dependency closure.
- **Its memory.** With 34 distinct step modules loaded and eight concurrent
  runs, the host peaks at 2,268 to 2,289 MiB, about 59 MiB per loaded
  module, against a budget of 650 MiB.
  - A soak of 1,000 runs stays between 980 and 2,382 MiB, with no growth
    trend.
  - The engine process stays at 73 MiB.
- **A public synthetic reproduction.** Six Bun scripts each import one
  generated module of 40,000 distinct strings (4.2 MB), with one flow of one
  step and one of all six. The host's resident set after a full garbage
  collection is:
  - 44 MiB at connect;
  - 75 MiB after one module;
  - 121 MiB after six, about 9.2 MiB per further module.

- **Code and state.** Of a distinct module's 42 MiB, about 14 MiB is state:
  the objects its dependencies make when they load. The rest is code:
  source text and compiled code.
- **Identical sources.** JavaScriptCore shares some compiled code between

- **The kept metadata.** The runtime keeps each codebase script's whole

**Semantic probes.** These ran on Bun 1.3.10, outside the repository, on
C's packages:

- **A model registered twice.** Two scripts each register a Mongoose model
  named `Order`, with different schemas.

- **Strict mode.** A codebase script assigns to an undeclared variable.

- **A compiled host at run time.** A compiled host imports at run time only
  files that need no package. It resolves no package from disk at run time

  compiled into the host.

## Options considered

Each figure says how it was measured: **host** is host mode in the compiled
host; **model** is the loader model, for a layout the runtime cannot load
yet.

| Option | S, per further module | C, 34 modules | Module state between scripts | CommonJS codebase scripts |
|---|---|---|---|---|
| per-script (today, 0006) | 6.3–6.7 MiB (host) | 1,911 MiB with 8 concurrent runs (host) | separate | the CLI's format |
| (a) shared chunks (0006 option 4) | 0.5–0.6 MiB (model) | 120–129 MiB (model) | shared | become ES modules |
| (b) host-provided packages | none: S's module is a file, not a package (listing it as a file, D12 today: 0.11 MiB, host) | 127 MiB (model) | shared, with the host too | unchanged |
| (c1) one instance per package | none: S's module is a file, not a package | 132 MiB (model) | shared for packages | unchanged |
| (c2) shared code, instance per script | 0.15–0.17 MiB (host, prototype) | 475–492 MiB with 8 concurrent runs (host, prototype) | separate | unchanged |

### (a) Shared chunks: [0006](0006-module-state.md)'s option 4

The build bundles the scripts of one bundler and one set of settings
together, with code splitting. A module that two scripts import becomes one
chunk, evaluated once per process.

- **Memory:** one instance of the closure, measured in the model since the
  runtime loads no chunks: 120 to 129 MiB for C, and 0.5 to 0.6 MiB per
  further module for S.
- **Deviation:**
  - **Shared state.** Every module that two scripts import is one instance
    per process, so scripts share its state; the `Order` probe fails.
  - **A new format.** esbuild and Bun split ES module output only. A
    CommonJS codebase script, the CLI's default (WR-47), would therefore
    run as an ES module:
    - in strict mode, as the `ReferenceError` probe shows;
    - without `module` and `exports` of its own;
    - with `require` only because Bun provides it there, which Node would
      not.

    That goes beyond D13.
- **Opt-in:** a module-state mode, `shared`, chosen at build.
- **Trace and manifest:** the mode, and the chunks in the manifest; a new
  deviation.
- **CLI parity:** the parity check is unchanged, since it builds each script
  alone. What runs has another format and layout. Adding a script can move
  code between chunks, which changes other scripts' files.
- **Fresh mode:** unaffected, since a fresh process loads one script; it
  would run the per-script bundles.
- **Fence:** a chunk evaluates in the context of the first invocation that
  loads a script needing it. Its load-time timers and connections are module
  state (milestone C3b), which then serves every script sharing the chunk.
- **Host-provided modules:** their imports become shims inside chunks, as
  they are inside bundles.

### (b) Host-provided package modules

The host contract lists packages, such as `mongoose`, as host-provided
modules. Imports of them resolve to shims, and one instance per process
serves every script: the host's own in host mode.

- **Memory:** the build cannot list packages yet, so the loader model
  measures the mechanism.
  - **C.** Each step bundle resolves the six packages to shims that take a
    registered instance from the registry, and one instance of each is
    registered first, as a host registers its own. That holds 99 MiB once
    registered and 127 MiB with 34 modules, 0.66 to 0.68 MiB per further
    module: each script keeps its own code and the state it makes around
    the packages.
  - **S** has no package, so packages listed would share nothing. Listing
    its shared file, D12's route today, costs 0.11 MiB per further module
    (host). Listing C's shared module the same way holds 130 MiB with eight
    concurrent runs (host).
  - Only what is listed is shared, so the host must list nearly its whole
    closure, and memory grows again with every package it misses.
- **Deviation:** D12 widened. A listed package is one instance shared by
  the host and every script, so the `Order` probe fails. The host's version
  of the package, and its import-time configuration, reach the steps
  ([0010](0010-packaging.md), host-provided modules, items 5 and 6).
- **Opt-in:** packages in the host contract's `host_modules`. The contract
  would need each package's version and lock: 0010 refuses host-provided
  packages today because the contract has no place for a lock.
- **Trace and manifest:** the listed packages and their versions. The SDK
  would check the host's instances against them.
- **CLI parity:** unchanged; the runtime's bundles carry shims, as with D12
  today.
- **Fresh mode:** the bundled copy loads once per process, at registration
  rather than when the step's module loads (D12's load effects, 0010 item
  7).
- **Fence:** listed packages load at registration, outside every
  invocation, so nothing they start is fenced, as with D12 today.
- **Host-provided modules:** this option is D12 extended, and it needs two
  changes:
  - **A CommonJS shim.** Most packages are CommonJS, which D12 refuses
    (`host_module_commonjs`) because its shims take export names from a
    static scan.
  - **Packages behind a file inside the folder.** Listing such a file fails
    to build today (the probe above).

### (c1) One instance per package

The build leaves packages out of each script's bundle (esbuild's
`packages: external`), and the harness loads each once per process from one
copy. A module cache that evaluates identical dependency modules once,
keyed by their content, has the same effect.

- **Memory:** about 132 MiB for C with 34 modules, in the model. A compiled
  host cannot load the packages as built, since it resolves none from disk
  at run time, so the harness would need its own resolver.
- **Deviation:** every package, or every identical module, has one instance
  per process, so the `Order` probe fails. Which instance a script gets also
  depends on which other scripts loaded first.
- **Opt-in:** a build setting.
- **Trace and manifest:** the packages and their keys.
- **CLI parity:** the parity check is unchanged. What runs no longer inlines
  packages: tree shaking and interop then work across a package boundary
  that the CLI's bundle does not have.
- **Fresh mode:** one instance per process anyway.
- **Fence:** a package evaluates in the context of the first invocation that
  requires it, and later scripts share what it started.
- **Host-provided modules:** unchanged.

### (c2) Shared code, one instance per script

The build keeps the dependency modules of a group of scripts in one file
per process, and each script makes its own instance of them. This is the
decision below, which describes it in full.

- **Memory:**
  - S: 0.15 to 0.17 MiB per further module.
  - C: 475 to 492 MiB with eight concurrent runs, and 519 to 530 MiB peak
    after 1,000 runs, with 10.6 to 11.1 MiB per further module.
  - All 53 of the prototype's modules: 631 MiB.
- **Deviation:** none in module state. It changes only three things (D18):
  - where dependency code is, as stack text and in a load error's message,
    and the names and source text that bundling gives it;
  - when an ES module dependency's default export is read;
  - whether code, or a whole module, that a per-script bundle removed as
    unused can run.
- **The other aspects:** below, under the decision.

### (d) Other routes

1. **Recycling on a module count** (F3a's `modules` trigger) bounds memory
   by restarting the process. It cannot keep a working set of 34 modules
   under the budget without reloading them over and over: the first load of
   C's 34 modules took 3.6 to 3.8 s. It stays the backstop.
2. **JavaScriptCore's sharing of byte-identical sources** saves 8 of 42 MiB
   per module in the model. Bundles differ by their entry code, so a design
   cannot rely on it.
3. **The runtime's kept metadata** costs about 0.5 MiB per module. The
   runtime keeps only the fields it reads.
4. **An uncompiled host** costs 42 rather than 55 MiB per module in the
   model. Hosts compile for deployment, so the target below is set on a
   compiled host.
5. **`fresh`** is not available in host mode ([0006](0006-module-state.md)).

## Decision

A bundle can be built with **shared code** (`windmill-lite build
-shared-code`). It changes what `warm` and host-mode processes load. It does
not change what a script sees of its dependencies: each step keeps its own
instance of every module it imports, as on Windmill.

1. **Build groups.**
   - Scripts form a group exactly when their per-script bundles agree on
     four things:
     - **one bundler with the same effective settings:** target, format,
       `define`, `inject`, `loader`, and the transforms of 0010 that apply
       to them;
     - **one installation:** the folder's files for a codebase entry, and
       one lock's install for Bun-built scripts;
     - **one strictness:** they start in the same strictness.
   - So these fall in different groups:
     - ordinary Bun scripts and `//nodejs` scripts, which are built for
       other targets;
     - Bun-built scripts of different locks;
     - codebase entries with different settings (WR-47);
     - CommonJS entries with and without a leading `"use strict"`, which
       makes their bundled dependencies strict too.
   - Native scripts (`nativets`, `//native`) are in no group: each of their
     invocations runs in a realm of its own (D5).
   - A script's **dependency modules** are the modules its per-script bundle
     inlines other than its own entry file: the folder's and the codebase's
     other files, and the packages' files.
     - **Scripts importing scripts.** A script that another script imports
       is a dependency module of the importer, in the importer's instance,
       apart from its own module as a root, just as its per-script bundle
       inlines it.
     - **Injected files** are dependency modules too: the entry's `inject`
       files and the env rewrite's support module.
   - Host-provided modules, and what only they import, stay out (D12).
2. **One closure per group.**
   - The build writes one CommonJS file per group, its **closure**. It holds
     every dependency module that any script of the group reaches, each
     behind the bundler's lazy wrapper.
   - It exports a function that runs it for a fresh instance, with the
     step module's scope (item 3). Its entry hands back a table from each
     module's key to its initialiser, through a property of its own on the
     global object rather than its `module.exports`, so the instance's
     `module` stays the step's.
   - **The file** is in Bun's own form of a CommonJS module that a bundler
     wrote (`// @bun @bun-cjs`), which Bun loads without transpiling it
     again: a large closure that Bun transpiled would cost its first step
     module more than the per-script bundle does.
   - **A module is its resolved file,** as in the bundler's module graph. A
     group resolves in one installation, so a module's key is its path:
     from the sync root for the folder's and the codebase's files, and in
     the group's installation for a package's.
   - **Physical copies stay separate.** Each physical copy of a package
     keeps a module of its own, with the dependencies its own location
     resolves.
   - **What two scripts share.** Two scripts share a module's code exactly
     when they are in one group and resolve the same file. A workspace file
     that scripts of two locks import is a module in each lock's group,
     resolving its packages through that lock.
   - **Strictness.** A closure is strict exactly when its group's
     per-script bundles are. An ES module group's closure starts with
     `"use strict"`, as every module of an ES module bundle is strict.
   - **Settings.** The closure is built with the group's settings: the
     entry's `define`, `inject` and `loader`, and the define table and env
     rewrite of 0010, applied as for the group's own output format.
3. **One instance per script.**
   - **The script's module.** Each script's module in the shared layout is
     its own code, with every import of a dependency module resolved to its
     instance's table. A plugin that only maps paths does this, as for
     0010's other transforms. The script's own code and its dependencies
     reach one instance of each injected module, as each module of a
     per-script bundle imports the one copy that esbuild injects: the
     script's module injects a proxy that re-exports the file's names from
     its instance.
   - **Making the instance.** When a step's module loads, it makes its
     instance of the closure with its own `module` and `exports` (a
     CommonJS module's; an ES module has neither, as Bun runs it),
     `require`, `__filename` and `__dirname`, and, for an ES module group,
     its own `import.meta`. Dependency code that reads them, changes the
     step's `module.exports`, or requires a file at run time, sees the
     step's own, as in its per-script bundle (WR-50). A dynamic `import()`
     resolves from the file that holds it, whatever the instance passes, so
     item 5 keeps such a script on its per-script bundle.
   - **The `import.meta` parameter.** A bundler replaces only free
     references with a define, so a binding of the parameter's name in a
     dependency, at its top level or as a function's parameter, would
     capture `import.meta`. The closure's parameter is therefore the first
     of `__wl_meta`, `__wl_meta_2`, … that no input of the closure spells,
     as 0010 chooses the env rewrite's binding.
   - **`import.meta.env`.** For an ES module group, the define table's
     rewrite of `import.meta.env` applies to dependency code as it does to
     an ES module bundle.
   - **When a module initialises.** A dependency module initialises in the
     step's instance the first time the step reaches it. Cycles initialise
     as in the per-script bundle. A dependency the step never reaches never
     runs in its instance. Dependencies initialise in import order, ES
     modules and CommonJS ones alike, as in a per-script bundle: esbuild
     0.28.0 and Bun 1.3.10 both keep import order there (esbuild splits the
     entry's code around each hoisted ES module).
   - **How a script reaches a dependency.** A CommonJS dependency is
     reached through a CommonJS reference, with the bundler's interop as in
     the per-script bundle. An ES module dependency is reached through an
     ES module reference, which re-exports the module's named exports, live
     through getters, and exports its default. A CommonJS reference alone
     would not do: a bundler gives an ES module importer Node's interop
     with a CommonJS module, whose default import is the whole exports
     object (Bun does so always). A named import is read from the module at
     each use, so live bindings still hold.
   - **Pruning.** An import that the per-script bundle drops whole, such as
     a `sideEffects: false` module whose exports are unused, is dropped in
     the shared layout too, unless another script of the group reaches the
     module (D18, unused code).
   - **The cost.** The closure's code is read and compiled once per process.
     What a further step module costs is the state its dependencies make
     when they load.
4. **What differs: D18** ([0001](0001-equivalence-contract.md)).
   - **Stack text and messages.** Stack frames of dependency code name the
     closure file and its lines, not the step's module. That includes the
     log tail that an error at module load leaves in the step's
     `ExecutionErr` message, where it can also move what the tail's
     truncation keeps.
   - **Names and source text.** A closure bundles another set of modules
     together than each per-script bundle, so the bundler can rename
     another set of colliding top-level names. The CLI's settings leave
     esbuild's `keepNames` off (WR-47), so a renamed function or class has
     another `.name`, and `Function.prototype.toString` of dependency code
     returns the closure's text.
   - **Default exports.** An ES module dependency's default export is read
     when the step first reaches the module, so a default export that the
     module reassigns later (`export { x as default }`, then `x = …`) keeps
     the value it had then; its named exports stay live.
   - **Unused code.** A closure is the union of its group's scripts. Code
     that a per-script bundle removed as unused and free of effects can run
     in the shared layout when another script of the group uses it. That
     covers two kinds:
     - a `/* @__PURE__ */` initialiser of an export only another script
       uses;
     - a whole module: the sibling that a `sideEffects: false` package
       re-exports beside one the step uses.

     That shows only where the code had effects after all (an annotation
     that does not hold), and as time and memory.
   - Nothing else differs, and `fresh` removes D18.
5. **Where a script keeps its per-script bundle.** In some cases one shared
   closure cannot reproduce the per-script bundle. There, `warm` and host
   mode run the script's per-script bundle, the build warns
   `shared_code_fallback` with the reason and the module that causes it,
   and the script's metadata says so. The cases:
   - **A `banner`** on its group's entry. A banner runs at the top of each
     output and declares bindings that both the entry's code and its
     dependencies' may read; this applies to the whole group.
   - **An object or array value in its entry's `define`.** esbuild makes one
     object per bundle, shared by the script's own code and its
     dependencies alike; this applies to the whole group.
   - **Top-level `await`** in a dependency module it reaches. A CommonJS
     closure cannot initialise such a module.
   - **A static external import from a dependency module in an ES module
     group.** In the per-script bundle it stays an `import`, loaded
     asynchronously and resolved with the `import` conditions. The CommonJS
     closure would turn it into a synchronous `require`, with the `require`
     conditions, which cannot load a module with top-level `await`. In a
     CommonJS group both layouts already `require` it. A module the runtime
     has built in (Node's, with or without `node:`, and Bun's own) loads the
     same either way, so an import of one is not external here.
   - **A dynamic `import()` that the bundler keeps in a dependency module it
     reaches, in any group.** That is one whose specifier the bundler cannot
     resolve at build, such as `import(spec)` with a variable, or one that
     names an external module. esbuild keeps such an expression, even in
     CommonJS output, and it resolves from the file that holds it.
     - In the per-script bundle that file is the step's own module, so a
       step-local asset resolves.
     - In a closure it would be the closure file, and the instance's
       `require`, `__filename` and `__dirname` do not change that.
     - Routing it through the step's `require` instead would lose its
       asynchronous loading and its `import` conditions.

     A `require` with a variable specifier needs no fallback: it goes
     through the instance's `require`, which is the step's. The build finds
     a kept `import()` by parsing the closure bundle, so text that only
     looks like one, in a string or a comment, does not count.
   - **A cycle through its own entry:** a dependency module that imports the
     script's own entry file.
   - **A namespace object that its entry and a dependency module both
     take,** of one ES module dependency. In the per-script bundle that is
     one object. In the shared layout the entry's would be its reference
     module's and the dependency's the closure's, two objects, and no
     bundler interop makes them one. A module takes a namespace object by a
     namespace import (`import * as ns`), a namespace re-export
     (`export * as ns from`), or an `import()` of a literal specifier,
     which the bundler resolves to it. A script where only its entry, or
     only its dependencies, take it is shared, since each side then sees
     one object.
6. **The bundle.**
   - **What stays.** The bundle keeps the per-script bundles byte for byte
     as without shared code. The parity check keeps comparing them with the
     CLI's uploads, and `fresh` runs them, so the uploaded bytes stay the
     CLI's and only what `warm` and host mode run differs.
   - **What shared code adds.** It adds the closures and each script's
     shared-layout module.
   - **The manifest** records `shared_code: true`, lists the closures with
     their digests, and lists D18 among the bundle's deviations. Each
     script's metadata names its closure, or the reason it falls back.
   - **A run's trace** records shared code beside the module-state mode, and
     lists D18 among its deviations.
   - **Open** follows the manifest; `ModuleState: fresh` runs the per-script
     bundles.
7. **The settle-time fence (D9)** is unchanged.
   - Making an instance is part of loading the step's module, which runs in
     the loading invocation's context. The timers and connections that
     dependency code starts while loading are module state, which the fence
     leaves alone (milestone C3b).
   - A dependency that a running invocation first reaches later initialises
     in that invocation's context, as a lazily required module does in a
     per-script bundle.
   - Compiling the closure runs none of its code.
8. **Host-provided modules (D12)** are unchanged.
   - Imports of a listed module resolve to its shim in the shared layout
     too, so it stays one instance shared by the host and every step.
   - A host that wants one instance of a package for its steps lists a
     module that holds it, as today.
   - Host-provided packages (option b) are not added: they would share
     state between steps, which shared code avoids.
9. **Not the default.** A bundle built without the flag runs as today. A
   later record can make shared code the default of `warm` once the suites
   have run both ways.

**Memory target.** The target is the host's budget, for the host's shape:

- **The shape:** a compiled Bun 1.3.10 host serves one bundle of 53
  CommonJS codebase scripts of about 6.9 MB each that share one dependency
  closure.
- **The target:** with 34 distinct step modules loaded and eight concurrent
  runs, its peak resident set stays at or below **650 MiB** through a
  1,000-run soak.
- **On the public closure C,** the prototype holds 475 to 492 MiB with eight
  concurrent runs and 519 to 530 MiB at its peak.
- **The gate,** on the real shared layout: `TestModuleMemoryClosure` and
  `TestModuleMemory` assert it.
  - C: at most 650 MiB peak after its 1,000 runs, and at most 16 MiB per
    further module after a full collection;
  - S: at most 1.5 MiB per further module.
- **Measured** on macOS, in two runs: S costs 0.17 to 0.21 MiB per further
  module; C holds 439 to 450 MiB with its 34 modules loaded, 453 to 462 MiB
  with eight concurrent runs and a 492 to 497 MiB peak after 1,000 runs, at
  9.9 to 10.3 MiB per further module.
- **On its own bundle,** the host re-measures before it relies on the target.

**Why not the others.**

- **(a), (b) and (c1)** save more memory, but each shares module state
  between scripts, which Windmill never does; the `Order` probe breaks
  under all three.
  - **(a)** also turns CommonJS codebase scripts into strict ES modules.
  - **(b)** also ties steps to the host's package versions and needs the
    host to list nearly its whole closure.
  - **(c1)** also needs a resolver of the harness's own in a compiled host.
- **Shared code** meets the target with the smallest deviation: per-script
  module identity, D1 and the scripts' own semantics stay as in `warm`.

## Consequences

- **What memory tracks.** A further step module costs the state its
  dependencies make when they load (C: about 11 MiB), not their code. A
  host whose dependencies make much state at load still grows per module.
  Its next steps are listing the modules that hold that state as
  host-provided modules (D12, as it stands) and the recycle triggers.
- **First invocations are faster:** C's 34 modules loaded in 0.31 to 0.58 s
  rather than 3.6 to 3.8 s.
- **The build** makes one more product per script and one closure per
  group.
- **Conformance** gains a configuration: D18's step cases run in `warm`
  from a bundle built with shared code, and the flow suite in `warm` and
  host mode from bundles built with it. That is the cost 0006 named for
  `shared`, accepted here for a host that needs it.
- **Two findings for 0010** come from the probes:
  - a host-provided file inside the folder that imports packages fails to
    build;
  - a compiled host resolves no package at run time.
- **Two tests in the repository.** `TestModuleMemory` runs S in the three
  layouts wherever the host-mode tests run. `TestModuleMemoryClosure` runs
  C behind `WL_MEMORY_PROBE`, since it needs the network once and about
  2 GiB. Both run the real shared layout.
